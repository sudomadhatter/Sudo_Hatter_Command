Proven twice: manual dispatch → issue #20; fully autonomous front door → drill fatal `PYTHON-FASTAPI-B` (numeric 7607174913) dispatched in **15 seconds**, issue #21. `TARGET=routines` = the FALLBACK thin pager (`POST /api/incident/fire`), Claude Routines itself is dead (no trigger API).

**Why:** future incidents, drills, and replication on other projects run against these contracts; the plan doc's §6 replication playbook (`_my_resources/diagrams_guides/security/sentry_error_response_team.md`) is the full recipe.

**How to apply:**
- Probe contract (fallback lane): unauth POST `/api/incident/fire` → **401 = armed**, 503 = secrets lost, 404 = router gone.
- Full-chain drill: send an UNTAGGED fatal via the project DSN with a FRESH unique message (same message = same group = no first-seen fire), then **check the Actions run list within ~30s**. Phantom-failure lesson: we hunted a "missing" dispatch while the run sat there succeeded — numeric-id vs short-id (7607174913 = PYTHON-FASTAPI-B) plus a timestamp misread manufactured two events out of one. Resolve both id forms before concluding anything.
- Loop guard is sacred: page events carry `incident_page=true`; the rule filters `incident_page is not set` (dedupe can't stop page loops — fresh id per hop).
- Page format (PR #22, agent lane): headline from the issue TITLE + the report's own `## TL;DR` (500-char cap) + report/branch links + tap-to-copy **Error Team Prompt** (`parse_mode=HTML`, `<pre>`). Telegram hard-400s the WHOLE message on invalid UTF-8 or bad HTML → `LC_ALL=C.UTF-8`, `iconv -c`, entity-escape every dynamic field; extraction best-effort (`|| true`, if-then) under Actions' `-e -o pipefail`. Fallback lane uses the same "Error Team Prompt" label (parity, commit 753edd26).
- **Apostrophe-in-`${VAR:-default}` = parse-EOF bug (fixed 2026-07-14, commit 821edfec).** The Error Team Prompt block (`cd0494b6`) shipped `${ISSUE_URL:-the repo's issues ...}`; inside `$(...)` bash re-parses the `:-word` default and the `'` in `repo's` opens an unterminated single-quote → `unexpected EOF while looking for matching '` → **exit 2**. It killed the report-ready page, flipped the job to `failure()`, and fired the FALSE `🛑 AGENT LANE FAILED — no report was produced` alert even though issue #23 + fix branch were produced fine. **Why all the Telegram testing missed it:** (1) the bug is in the *unexpanded* `${:-default}` syntax — any test running the curl with vars already substituted never touches the apostrophe form; (2) apostrophe-inside-double-quotes reads as safe (the `${:-word}` re-parse quirk is obscure); (3) YAML lint validates structure, not embedded-bash quote matching; (4) the step only runs on a real `repository_dispatch`, and none fired between the `cd0494b6` merge and the first live incident (04:43Z 2026-07-14) — its maiden run WAS the failure. Fix: drop the apostrophe; `git ls-remote origin` (also failing auth here) → `gh api` for the branch lookup; `continue-on-error: true` on the success-page step so a paging glitch can never masquerade as a lane failure; bumped checkout@v5/auth@v3/setup-gcloud@v3 (Node 20 dep warning). **Lesson: lint/drill can't catch a shell parse error in a rarely-run step — a heredoc `bash -n` (syntax-check) gate on the page step, or a real dispatch drill after ANY edit to the page bash, is the only thing that would.**
- claude-code-action@v1 has NO `mode:`/`prompt_file:` inputs — only `prompt:`; verify against action.yml, not memory.
- Windows gotchas: ASCII-only curl JSON bodies (em-dash → FastAPI 400); emoji typed into shell commands reach Telegram as invalid UTF-8 → write a UTF-8 file and `--data-urlencode "text@C:/path"` (Windows curl wants `C:/` not `/c/`); `.env` values carry CR tails → `tr -d '\r\n'`.
- The user auth token has NO issue/event scopes (by design) — resolve/list Sentry issues via the Sentry MCP (`update_issue`), rules via curl per [[sentry-api-access-aviationchat]].
