## The problem, stated once

The launcher fix was only ever **half applied.** `Sync-AntigravityWorkflowMirror` in
[sync-agents.ps1:583](../../../.agents/scripts/sync-agents.ps1#L583) emits a thin launcher **only** when the
command body is over 11,500 bytes; anything smaller still ships to Antigravity as a verbatim mirror.

Measured on `e54e0c37`, in `.agents/workflows/` (39 doors, `INDEX.md` excluded):

| Shape | Count |
|---|---|
| generated thin launcher | 25 |
| **verbatim mirror** | **13** |
| hand-authored launcher (`smh-adviser-board`) | 1 |

That surviving conditional is why the 12,000-char cap keeps resurfacing in every session. It is still an
**operative rule** — a thing an agent must measure against — and it is therefore restated in 39 generated
door files, 8 script comments, 8 documentation sites and 5 memory files. Delete the conditional and the cap
becomes **structurally unreachable**: no door can ever be large enough to truncate, so nobody has to reason
about size again.

> Operator, 2026-09-01: *"We are making that much harder than it has to be. lets do a simple fix and have
> them all thins that point to the real commands. then we need to clean up all the memorys and reminders
> about the 12k rules that slow everything down everytime"*

**Consequence for the operator:** the `/` menus do not change. Every command still runs identically on every
platform **from the lobby**. What changes is that the cap stops being something anyone — operator or agent —
has to hold in their head, and 39 door files stop carrying a sentence about it.

### ⚠️ AUDIT FINDING F1 — the one real behaviour change, stated before it is decided

There is exactly one place where behaviour changes, and it is worth naming before the work starts.

`docs/workspace-standard.md:293` says: *"A launcher only resolves where `.agents/commands/` exists — the
lobby. Under the thin model a project carries no tier-1 copy, so a **big** command invoked from the global
menu inside a project STOPS and says so, rather than running."*

Measured: **7 of the 10 folders under `Projects/` carry zero `.agents/commands/*.md`** (only the three
legacy/unmaintained ones — `B-L-WorldWide`, `BRKN_Tattoos`, `sudo-command-center` — still have copies). So
today, invoking one of the **13 currently-verbatim** commands from Antigravity's *global* menu while standing
inside a thin project **runs it**, because the global cache holds the whole body. After this change it
**STOPS** and tells the operator to run it from the lobby.

**Decision: accept the trade.** Three reasons, in order of weight. It is the *same* trade already in force
for the other 25 commands, so this makes one rule out of two. Twelve of the thirteen are lobby commands by
design — every `cicd-*` is labelled *"Command center → child project"* and every `smh-*` acts on the command
centre itself, so invoking them inside a project was already the wrong door. And the standard already argues
this direction is correct in its own words: *"A command that fails visibly beats one that runs on 27% of its
steps."*

**The one to watch:** `sentry-security-team-avch` is the single member of the thirteen that is genuinely
project-scoped (AVCH), and therefore the only one a person might reasonably invoke from inside a project. If
that ever bites, the fix is to run it from the lobby — not to restore the size branch.

Step 4 must therefore change that sentence's **"a big command"** to **"any command"**, or the standard will
describe a rule that no longer exists.

## Out of scope — decided, with evidence

**`smh-adviser-board` stays hand-owned** in the sync's `$excluded` list. Its launcher carries

> *"This surface runs INLINE. Antigravity workflows cannot spawn subagents, so read

are. The one door that is *legitimately* not generated stays legitimately not generated, and the new `CS-18 O`
check names it as the single exception rather than exempting a category.
