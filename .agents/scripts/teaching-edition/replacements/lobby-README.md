# Command Center

A workspace that turns AI coding agents into a development team with actual process — planning gates,
tests that have to pass, code review, and a written record of every decision.

There is no framework here and no database. **The folder structure is the program.** Markdown files
describe how an agent should behave, and the agent becomes what the files describe. That means the
whole system is plain text, version-controlled, greppable, and yours — it lives in your repo rather
than a vendor's memory, and it works the same in Claude Code, opencode, Antigravity, and Codex.

---

## Start here

```bash
git clone <this-repo> command-center
cd command-center
cp .env.example .env        # then fill in the two REQUIRED keys
```

Open the folder with your agent and type:

```
/sudo-tour
```

Six stops, from this empty clone to a story that actually shipped — on a real project of yours, not a
toy. It resumes wherever you left off; just run it again.

**Training mode is on.** A `.training-mode` file at the root tells agents to teach as they go: explain
before executing, define every term, and answer questions with the reasoning behind them. Turn it off
whenever you are ready with `/training off`. It is reversible, and nothing in the system is gated
behind it — what is left when it goes is the real system, not a reduced one.

## The two rules everything else rests on

**Plan first.** No file is modified until you approve a written plan. The agent researches, writes an
`implementation_plan.md`, shows it to you in chat, and stops. This will feel slow exactly once. Then
it will feel like the only sane way to work with something that can rewrite forty files while you
are getting coffee.

**`main` is not the working branch.** Day-to-day work lands on `main_debug`. Promoting to `main` is a
deliberate, human decision. "It works" and "it is safe to ship" are different claims, and keeping two
branches is what keeps them different.

## What is in here

| Folder | What it holds |
|---|---|
| `.agents/` | The toolkit — `rules/` (how agents behave), `commands/` (the `/slash` commands), `skills/` (specialist know-how loaded on demand), `workflows/`, `scripts/`, `templates/` |
| `.claude/` `.opencode/` `.antigravity/` `.agent/` | Per-tool copies so commands resolve in whichever agent you run. Generated by `/sync-agents` — never hand-edit them |
| `docs/` | The reference shelf: the site map, the workspace standard, the quick reference |
| `_bmad/` | The BMAD method module — the agile lifecycle from product brief to retrospective |
| `Projects/` | Empty. Your projects go here, each its own git repo |
| `_artifacts/` | Empty. Session memory — plans, walkthroughs, decisions — written as you work |
| `AGENTS.md` | **The brain.** The routing table: *this kind of work → read these files.* Read it first |
| `router.md` | The directory of projects. Empty until you add one |

`CLAUDE.md` and `GEMINI.md` are one-line adapters that both say "read `AGENTS.md`" — one front door
per tool, one brain.

## The dev loop

Once you have a project and a backlog, every story runs the same three steps:

| | Command | What it does |
|---|---|---|
| ① | `/sudo-write-story-tests` | Writes the story spec, then **failing** acceptance tests — before any code |
| ② | `/sudo-dev-story-tests` | Plans, stops for your approval, implements until the tests pass |
| ③ | `/sudo-code-review` | Adversarial review + the test and clean-code gates → PASS / CONCERNS / FAIL |

Then `/sudo-update-sprint-memory` closes the story and files what was learned.

Each story runs in its own **git worktree** — a separate folder sharing one repository — so parallel
work never mixes in the same files. Ask any agent here to explain any of this; that is what training
mode is for.

## Getting a project

Clone the **project skeleton** — a companion repo with the stack, the BMAD module, and the test bench
already wired. `/sudo-tour` stop 2 walks the whole thing including the GitHub setup.

> **The skeleton is a template, not a workshop.** Clone it per project; never build inside it.
> Building in the template tangles your first project with template history and leaves you without a
> clean template for the second.

There is also `/new-project` for a lightweight workspace with no BMAD module, no test bench and no
app scaffold. Use it for a utility folder; use the skeleton for anything you intend to ship.

## A note on what you are looking at

This is a generated, shareable edition of a working command center — exported by a script that ships
the system and none of its owner's projects, history, or notes. So you are getting real machinery
that has been used in anger, with the personal layer removed rather than a demo built to be shown.

A few things are therefore blank on purpose and are meant to be filled in by you: the routing table in
`router.md`, the maintained-projects list, and — most importantly —
**`.agents/rules/operator-profile.md`**, which describes who the agent is working *for*. It ships as a
template. Fill it in early; it changes how every reply is written.
