`hooks_armed.py` (SCC-110) answers the question every other gate here quietly assumes: **did the hooks run at all?** **Five** things switch a gate off and each is silent on its own — `core.hooksPath`, UNTRACKED and per-machine, so a fresh clone has it unset and reads an empty `.git/hooks`; the **inner script**, since every dispatcher in `.githooks/` ends `[ -x "$SCRIPT" ] || exit 0`, so deleting it *or merely dropping its executable bit* makes the hook exit 0 with no output at all; the `<NAME>-ENFORCE` flags, whose absence downgrades a gate from *reject* to *warn*, which reads as success because VS Code renders hook output nowhere the operator looks; an **orphaned flag** — tracked, while the gate script it names is not, so the marker claims a gate that does not exist (the whole-repo case: declares a Jira project, tracks zero gate scripts); and the **dispatcher**, a flag arming a script reached through a hook that is not tracked, so nothing dispatches it. ⭐ **The flags are read from the INDEX *and* from DISK (SCC-140).** Every consumer reads them off the filesystem — `commit-msg-jira.sh`, `pre-push-main-approval.sh`, and `sop_currency.py` via `.exists()` — and `sop-currency.sh` documents *"delete the flag"* as the disarm, so an index-only check reported ARMED to an operator following this system's own written instructions. It said **three** until SCC-140 measured it green on the other two. ⭐ **The expected set comes from `git ls-files`, not from a directory listing, and that distinction is the whole correctness of the script.** A listing cannot tell *"this gate was deleted"* from *"this repo never had that gate"* — the first cut of this file used `iterdir()`, skipped any script absent from disk, and so reported **ARMED with zero findings** on a repo whose three gate scripts had all been removed and whose every hook was therefore allowing operations unchecked. Asking the index answers both, ignores untracked junk (a stray `.DS_Store` is not a broken hook), and makes the word "tracked" in its own error text true. The flag→script pairing, by contrast, **is** declared and has to be: `.githooks/commit-msg` dispatches both `commit-msg-jira.sh` (`JIRA-ENFORCE`) and `sop-currency.sh` (`SOP-ENFORCE`) — two flags through one hook file — and `SOP-ENFORCE` names no `.githooks/sop` for any filename rule to find; an unknown flag is reported rather than swallowed. That table governs the flag question **only**: executability is checked for every tracked gate script, because `pre-commit-encoding.sh` is armed unconditionally and has no flag, and a flag-keyed check would have exempted the one hook the silent-`exit 0` finding applies to most. It **reports and never arms** — rewriting a machine's git config out from under the operator is worse than telling them, and the printed remedy is deliberately per-repo, not `--global`, since a relative path set globally arms `.githooks/` in every clone on the machine. `task_preflight.py` folds it in as ERRORs on purpose: that file's VERDICT prints *"clear to close out and merge"* whenever the error count is zero, so a warning would leave the clean line standing on a repo whose gates never ran. One finding is conditionally softened — a repo that never **claimed** gates (no `jira.conf`, no gate scripts) warns rather than blocks, because several `Projects/*` ship no hooks and never did; a repo that claims them and tracks none is drift, and blocks.

`evidence_extract.py` (SCC-123) is the **only script here that is not a gate** — it refuses nothing, no hook calls it, and no operator types it. It is the review engine's fact-fetcher, ported from pr-af's `evidence.py` @ `8593130`, and it exists because a review lens that cold-reads a repo only reasons about what it happens to open. `--pack` primes a lens before it reviews (target files plus who imports them); `--findings` pulls ground truth for an asserted finding (the code at the line, its call sites, the diff hunk, cross-referenced files). ⭐ **Every cap was re-read at the port SHA rather than copied from notes, and they are NOT in that project's `config.py`** — at `8593130` that file holds only an on/off toggle, and the numbers live in `evidence.py` as constants its orchestrator never overrides; each one is cited line-by-line in the module docstring. **The search is pure Python — a shelled-out `grep` is banned outright** (it is not portable across this system's two machines), and the guard proves that by running the script in an interpreter where **process spawning is impossible** and requiring byte-identical output. ⚠ That proof was nearly vacuous: emptying `PATH` does *not* stop a child finding `/bin/grep`, because CPython falls back to `os.defpath` — the author's own mutation run caught it, and the block now goes in via `sitecustomize`. Two deliberate divergences from the port, both because the naive version fails **silently**: `_python_module_names`/`_python_importers` (Python) and `_ts_importers` (TS/JS) replace `_path_to_module`, which returned one dotted name and emptied `IMPORTED BY` for every TypeScript file *and* for every script in this repo (`wf_common.py` is imported as bare `wf_common` off a `sys.path` entry, never as `.agents.scripts.wf_common`); and the pack emits its import context **above** the body, since one 400-line file fills the 16 000-char budget and truncation was eating the dependency map — found by running it on `wf_common.py`, not by a fixture. ⛔ Do not deduplicate it into code-graph calls (that index is machine-local, stale after a pull, and misses attribute dispatch — the duplication is the point) and do not grow it into a blast-radius tool.

`label_tasks.py` (SCC-56; renamed and made two-mode by SCC-155) backs **`/cicd-label-tasks`** (a BMAD epic's stories) and **`/smh-label-tasks`** (a Task's subtasks), and the split of labour is the design: the **script** does the set math and the board writes, the **agent** reads the story files. That is not squeamishness about parsing — telling *"will modify"* from *"mentions"* is a judgment no parser wins. Across 139 AGY story files, 105 name source paths, 58 carry negative declarations, and only 29 have a `**Task**` checklist, so there is no field to read; story 19.1 names `google_llm.py:119` (a path inside the venv — a reference) and says *"NO `firestore_session.py` changes, that is 19.2 entirely"*, a negative declaration handing a file to a named sibling. Three things it derives rather than asks: the **repo** (the parent key's project prefix matched against each repo's own `.agents/jira.conf`, lobby included — so adding a project is zero edits, and two repos claiming one key is reported as the misconfiguration it is); the **base ref** for a story branch diff (**this** epic's `epic/*` branch by key, else `main` — never another epic's, which the retired board's "exactly one live epic branch is the normal case" fallback would have done, and AGY has two live right now); and **umbrella** children (a BMAD number that prefixes a sibling's — `12.3` over `12.3.4`/`12.3.7` — contains them rather than competing, found when the first live run had `AVCH-14` inherit all eight `story-12-3-*.md` files and lock against everything it contained). The approved set is the largest in which **every pair** is disjoint, computed exhaustively and deterministically because a stamp only means something if the same input gives the same set. Planning dirs never count as overlap; `docs/` deliberately does **not** join that list, since projects ship from it and over-excluding manufactures false greens. `stamp` **rewrites** `parallel-ok` across the whole parent rather than adding it — the strip is what makes a parent-scoped writer self-correcting where ①'s per-story one rotted. Since SCC-155 it stamps **`quick-dev`** the same way, through a tri-state `label_plan()` whose third state is the load-bearing one: a child the pass did not assess is left ALONE, so a re-run never strips a label somebody set by hand. Task mode grounds a subtask through the sibling `task.yaml`'s `task_key` (exact-matched, so `SCC-146`'s manifest never grounds `SCC-14`) rather than by slug, because a Task lane's artifacts folder carries no key. The two modes refuse INTO each other by name, and neither ever names the retired `/cicd-parallel-check`. A grounded child with no touch-set is a hard refusal, never an assumed-empty set. `check` compares the stamped child list against the epic's current children: a set that has moved reads *"re-run me"*, which is the detector the sprint dependency map and the `Deferred` saved filter both lacked when they misled on 2026-08-09.

`split_sprint_status.py` ran the AGY migration 2026-08-03 (baseline `0752c437`): board 363,334 → 62,040 B in four staged applies, each `verify`d **byte-identical** by reconstructing the original from (board + history + manifest) — never peeking at the blob — and comparing against `git show <sha>:<path>`, the LF stream (the worktree stream varies by machine — `* text=auto`). Narrative now lives in `_bmad-output/history/<epic>/<key>.md` + `CHANGELOG.md`; the board carries bare `key: status`, a ≤120-char note on live rows only, enforced by `workflow_lint.check_board_note_budget` (a note on a `NO_NOTE_STATUSES` row is an ERROR; `story_status.py set` drops it on the flip automatically).

`gate_receipt.py` has no `--result` flag by design: it EXECUTES the gate and writes the receipt from the real exit code, so a verdict cannot be handed in. All flags precede `--`; everything after it is the gate command verbatim. Staleness compares **trees, not SHAs** — a branch that lands via a merge commit has a new HEAD and identical content, and calling that stale is how a hard gate earns a permanent `--advisory`. **The Task lane rides it too (SCC-146):** `--root <task-artifacts-dir>` bypasses project resolution entirely — the lobby has no board for the resolver to find, and that one `die()` was all that kept receipts story-lane-only — and lands receipts at `<root>/gates/<gate>.json`, with `--task` as a plain alias for `--story`. Without `--root`, behaviour is byte-identical. **Root mode is hardened since SCC-154:** `run --root` REQUIRES `--cwd` (without it the gate executed inside the artifacts dir and recorded `fail` for a suite that never ran — a fabricated result from the tool whose point is that results cannot be fabricated), a relative `--root` resolves against `--cwd` rather than the invoker's cwd (from the wrong checkout the receipt landed as an untracked stray with success-shaped output), and `--project` beside `--root` is refused as the contradiction it is. The receipt now also records `dirty_paths` (additive; the recorder stays strict) so READERS can apply policy — `task_preflight` exempts `_artifacts/`-only dirt — and `receipt_defect()` is the shared result-validity half every consumer reads through.

`workflow_lint.py --staged [--fix]` is the **pre-commit encoding gate** (Wave 5): staged files only, encoding only, so it stays fast enough not to get disabled. Install with `git-hooks/install-encoding-hook.ps1 [-All]`. It resolves the hook dir from **`core.hooksPath`** first — the lobby, AGY and Fresh all set it to `.githooks`, so writing to `.git/hooks` installs a file git never reads; the first version of this installer did exactly that and reported success in three of four repos. It refuses to clobber a foreign `pre-commit` hook, and `scripts/git-hooks/DISABLE` (untracked) is the kill switch. `--fix` repairs only *unambiguous* cp1252 round-trips; everything less certain is reported, never rewritten.

**Every hook probes `python3 -> python -> py`, in that order** (aligned SCC-49). `pre-commit-encoding.sh` used to do `PY=$(command -v python || command -v python3) || exit 0`: it never tried `py`, so on a box with only the Windows launcher the substitution failed and the gate **exited 0 - armed in name, checking nothing, silently**, which VS Code's hidden hook output would have kept invisible forever. `.githooks/post-commit` had the same `python`-first order. Both now match `sop-currency.sh`, and the two armed gates ANNOUNCE a skip rather than taking it mutely. `test_jira_feed.py` guards the contract textually (the suite cannot execute a `.sh` on the PC) - reading CODE only, since the fix's own comment quotes the broken line and a raw grep would flag the fix as the defect.

`git-hooks/post-commit-jira-start.sh` (SCC-113) is the **second** `post-commit` recorder, and it exists because four transition seams wrote `Done` while exactly one wrote `In Progress` — the BMAD story lane — so on a board whose every non-epic ticket is a `Task`, nothing in the command centre was ever visible in flight. The trigger is deliberately **not** a command: `/smh-quick-dev` is not always run, and a fix that depends on remembering to run it re-creates the defect, so the signal is the first commit on a `chore/ · claude/ · epic/` branch — whatever route got there, a bare `git commit` included. It had to be `post-commit` and not the armed `commit-msg` gate, whose own header forbids growing it (*"a live 'does AVCH-57 exist?' call would put a network round-trip on every commit and would fail closed on a plane"*); `post-commit` carries the opposite contract — sealed commit, every error swallowed — so a network call is safe there and **never** blocks. Three properties are what make it cheap enough to leave armed, and all three are executed against a real git repo in `tests/test_jira_start_hook.py`: a marker under `--absolute-git-dir` short-circuits every later commit **before** any network call (one exchange per branch, ever — and the exchange is *three* acli round-trips, `view` → `transition` → the read-back, which is worth stating precisely because round-trip cost is the entire argument for `post-commit` over `commit-msg`); the marker is written **only on a SETTLED result** — moved, or already there — so an offline commit, a refusal, *and* a not-yet-startable status (`Blocking`, `In Review`, `Deferred`, which exit 3) all retry on the next commit rather than silencing the ticket forever; and the marker is named for the **branch**, not the key — a key-named one suppresses a second lane carrying the same key, which is exactly what a `Bug`-reopened ticket gets, and it was caught by the `claude/`/`epic/` cases failing for that reason instead of the one they were written for. The key comes from the branch matched against this repo's own `jira.conf`, so another project's key is ignored rather than mis-filed.

A file that legitimately **carries** those bytes as data — the detector's own constants, its fixtures, a doc quoting them — declares `wf-lint: allow-encoding-literals` and is skipped. Without it the gate blocks every commit that touches the gate.

`jira_feed.py` (SCC-49) is the only script here that WRITES to something outside the repo, so both of its write paths end by reading the ticket back: an `acli` call that exits 0 while recording nothing is indistinguishable from one that worked, and that is precisely the failure a prose instruction cannot catch. It renders, never invents — the story outline comes out of the story file's `## Story` block and `## Acceptance Criteria` list, and a story missing either renders `(none found in the story file)` plus a stderr warning rather than something plausible. `devrecord` keeps **exactly one** Dev Record per ticket by finding the existing one and updating it in place — and **since SCC-271 that is enforced, not merely intended**: `--append-new` over a ticket that already carries a record for the same `--story` id exits 2 and writes nothing (a second *lane* files under a different id, so it was never the banned case). Seven command bodies and the SOP had banned the flag in prose; nothing checked. In the other direction, `index-row` no longer reports the `(empty - …)` placeholder it deliberately replaces as data loss, so a `MISSING … line(s)` refusal from it is now always real: `/cicd-quick-dev` files a record when it closes its own branch and `/cicd-close-story-merge-tree` files one when it closes the story, and stacking those buries the current one. Its content is FLAGS FIRST (`--decision` / `--pitfall` / `--followon`, passed by close-out straight out of Step 3's learning routing) with a walkthrough scrape underneath as a safety net — an empty bucket renders `(none recorded)` and warns, and `--strict` makes it a hard fail. It resolves a project WITHOUT requiring a sprint board, because the command centre deliberately has none and its chore tickets still need records. `acli` comes from `--acli` / `$ACLI_BIN` / PATH, which is what lets the test suite drive the whole post-and-verify path against a stub executable. The work-item type is **derived**, in ONE place (`work_type()`), never defaulted - a fixed default is how the whole board ended up `Task`. `Story` = BMAD sprint work (debug stories included); `Task` = workflow/IDE/rules/skills work under a grouping epic; `Epic` is never computed. The PARENT is never the tell - everything is parented, and a BMAD epic is indistinguishable in Jira from a grouping epic. **`Subtask` is the one type `work_type()` does NOT answer** (SCC-119), and that is not an omission: a subtask is decided by its PARENT'S TYPE - `Epic` above it means Story/Task, `Story`/`Task` above it means Subtask - which is a board read, not a string test. `check_subtask()` owns it, and it checks PLACEMENT rather than type: no parent, parented straight to an Epic, nested under another subtask (hierarchyLevel -1 is the floor), or a parent lagging its own children. **None of those are auto-fixed** - re-parenting is a board move and which parent is right is a judgment about the work. Story takes THREE signals because none survives the board alone: the dotted number is true before the story file exists (backfilled rows), the `debug-` marker carries ids with no number of their own, the file catches the rest (`tea-16`). **`Bug` is never computed, and cleared in exactly one place** - it is a TEMPORARY flag meaning a Story or Task turned out to be broken, raised by an audit that traced a live bug back to the ticket that introduced it or by the operator by hand, carrying the same number and file as before, so a rule that 'corrects' it mid-flight erases the only signal that the work is broken. `devrecord --closing` puts it back to `Story` **or `Task`** at close-out - whichever `work_type()` says the ticket is - because that is the one moment anything can know the fix landed; the bulk `audit` cannot tell 'still broken' from 'fixed', so it reports Bugs and moves on. Restoring only to `Story` (SCC-49's first cut) stranded every flagged **Task** as a permanent Bug, since nothing else in the system can clear one; fixed in SCC-53. `audit [--apply]` reports and migrates a whole board, reading each ticket back. Model + the AVCH worked example: `.agents/rules/jira.md` SS Work-item types.

**The RAISE half (SCC-54)** is two verbs, and they are two on purpose. `trace --path <file>[:LINE]` reads git only — `blame` on an exact line (the strong signal: the commit that wrote *that* line), `git log --no-merges` on the file (the weak one: worked nearby) — and ranks the tickets whose commit subjects carry a key, filtered to the project(s) in this repo's `.agents/jira.conf` so commit prose saying "unlike AVCH-13" cannot nominate a ticket this repo could not close. `--no-merges` because a `--no-ff` merge subject repeats its branch's key and would double-weight whichever ticket merged last for no added information. It has **no board path at all** — a deliberately broken `--acli` cannot make it fail. `flag --key <K> --reason "..."` writes: `Story|Task -> Bug`, `Done -> To Do`, and a **Bug flag** comment carrying the reason, the evidence and *what the ticket was*, each read back. It is idempotent (two testers, one bug, no fight), refuses an `Epic` and - since SCC-119, for a different reason it states differently - a `Subtask`, whose refusal NAMES the parent to flag instead (a subtask is a leaf, not a container; breakage is recorded on the ticket that owns the job), and moves the status **only out of `Done`** — a ticket `In Progress` was never finished, and reopening it would erase real state to say what the type already says. **`flag` takes `--key` and only `--key`, never a trace result:** "which ticket last touched this line" is not "which ticket introduced this bug", and a wrong flip pulls an innocent ticket out of `Done` with no undo. `/cicd-live-testing-team` Step 3.5 is the wired entry point — it already files a bug doc per symptom with the fix-direction paths `trace` needs — and it stops for the operator between the two verbs.

⚠️ **The defect SCC-54 found underneath itself:** `--fields` on `acli workitem view` is a **whitelist**, and `issuetype` was not on the list `view_fields()` sent. Every type read in the file goes through there, so on the live board `have` came back `""` — `devrecord --closing` never saw a `Bug` and therefore **never cleared one**, and `audit --apply` reports FAILED on every conversion that in fact succeeded. It passed green for two tickets because the test stub returned the whole shape no matter what was asked for. **A stub more generous than the tool it stands in for tests nothing**; the stub now enforces the whitelist, with a positive control asserting it is still strict.

`task_preflight.py` (SCC-49) backs `/smh-close-task-merge-tree`, the **Task** lane's close-out — the half BMAD has no answer for, since `/cicd-close-story-merge-tree` needs a sprint board, a story file and an epic branch that task work does not have. It resolves the repo **without** a board, and every check in it was local until SCC-119 added exactly one that is not: `check_children()` refuses to close a PARENT while any subtask under it is still open, because the whole job closes together at the end. Three traps are handled explicitly and each one would have made it a gate that cannot fail - it reads the **exit code, never the row count** (a bad key and a childless parent both return zero rows, so counting rows turns a wrong key into a clean pass); it never asks for `parent` in `--fields` on a search (the real acli exits 1, straight into the first trap); and it resolves `acli` gently instead of through `acli_bin()`, which DIES when the CLI is absent and would have taken an offline-capable preflight down with it.
